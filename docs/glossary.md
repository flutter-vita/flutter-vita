# Glossary

Shared vocabulary for `flutter-vita`. Two worlds collide in this project — the
Flutter/Dart world and the Vita homebrew world — and most confusion comes from
a term meaning something specific in one of them. Terms marked **(ours)** are
project-invented and should be used consistently in code and PRs.

## Vita platform

| Term | Meaning |
|---|---|
| **VitaSDK** | The community toolchain for PS Vita homebrew. Target triple `arm-vita-eabi`, C library is newlib. Ships headers and stub libraries for Sony's `sce*` APIs. |
| **HENkaku / h-encore** | Homebrew enablers for retail Vita firmware. They are what makes an unsigned title runnable at all. Assumed present on any target device. |
| **taiHEN** | The plugin framework HENkaku installs. Kernel plugins run through it. Explicitly *not* a dependency of this project ([ADR-0001](adr/0001-aot-only-no-jit.md)). |
| **Float ABI** (`soft` / `softfp` / `hard`) | Where floating-point arguments physically live at a call boundary. `soft` emulates FP in software and passes in integer registers; `softfp` uses the FPU for arithmetic but still passes in `r0`–`r3`; `hard` uses the FPU *and* passes in VFP registers `d0`, `d1`, … Note softfp is **not** slower at arithmetic — only at argument passing. **A mismatch links cleanly and then silently corrupts every `double` crossing the boundary**, which is why [Phase 0.5 B5](phase-0.5-feasibility.md) checked it before any code was written. VitaSDK is `--with-float=hard`; Dart's GN defaults ARM to `softfp`, so patch 0004 overrides it as a default rather than a `gn` argument that could be forgotten. |
| **ELF** | Executable and Linkable Format — the standard Unix binary container. Header (`e_machine`, `e_flags` — how the float ABI was verified), sections (`.text`, `.rodata` — the source of every size number here, plus `.ARM.attributes`), and segments (`PT_NOTE`, where `NT_GNU_BUILD_ID` lives). The Vita's SELF is an ELF variant, which is why the whole build pipeline composes: `.elf` → `.velf` → `eboot.bin` → `.vpk` is a chain of transformations on one format, not conversions between formats. |
| **SELF** | Signed ELF. The executable format the Vita loads. Produced from a plain ELF by `vita-make-fself`. Homebrew uses a "fake" self signature. |
| **eboot.bin** | The main SELF of a title, at `app0:/eboot.bin`. Our single statically linked binary ([ADR-0004](adr/0004-static-single-binary.md)). |
| **suprx** | A Vita shared module (dynamic library equivalent). Avoided by ADR-0004. |
| **Dynamic loader** / `dlopen` | The OS service that finds a shared library on disk at runtime, maps it into a running process, and resolves its symbols. **This platform has none for homebrew** — [ADR-0004](adr/0004-static-single-binary.md) is one statically linked `eboot.bin`. Our shim returns a null handle for every input and a real message from `dlerror` rather than `nullptr`, because a caller holding a null handle *and* a null error string has nothing to report. Its consequence is not cosmetic: it is the entire reason a `dart:ffi` package cannot work here without being statically linked first ([ADR-0013](adr/0013-ffi-needs-static-linking.md)). |
| **VPK** | The distribution package: a zip containing `eboot.bin`, `sce_sys/` metadata, LiveArea assets, and the app's data. Built by `vita-pack-vpk`. |
| **SFO** | `param.sfo`, the title metadata blob (title ID, name, category, memory-mode flags). Generated by `vita-mksfoex`. Notably carries the extended-memory request. |
| **Title ID** | Nine characters, e.g. `FLTR00001`. Identifies a title and determines its `ux0:app/<TITLEID>` install path. Must be unique per app. |
| **LiveArea** | The Vita's per-title home screen panel. A VPK needs its background, icon, and startup image or the title looks broken even when it runs. |
| **app0:** | The read-only mount of the running title's own install directory. Where `flutter_assets` and the ICU data will live. |
| **ux0:** | The main writable storage mount (memory card / internal). Per-app writable data goes to `ux0:data/<app>/`. |
| **CDRAM** | The Vita's video memory: **128 MB, physically separate** from the 512 MB of main RAM. Wired to the GPU and the display controller, which is why the framebuffer lives there — `sceDisplaySetFrameBuf` scans out of it sixty times a second. The catch is that it is fast for the GPU and **slow for the CPU**: uncached, so every write goes straight to memory. Our present path is a CPU `memcpy` *into* CDRAM, which is most of why the **Blit** below costs 8.06 ms. The frame log's three budgets — `user`, `cdram`, `phycont` — are separate pools that do not share. |
| **Common dialog** | A system UI panel the **shell draws into the running application's own frame**: the IME keyboard, message boxes, PSN prompts, the photo picker. Driven by `sceCommonDialogUpdate` once per frame with a render target the app supplies. It will only composite into a surface **GXM manages** — see the GXM entry — which is why text input needed graphics work in a port that renders entirely in software. |
| **Background app / `eboot2.bin`** | A second executable in the same `.vpk`, started by `sceBgAppUtilStartBgApp(0)`, that runs as a *separate process* and so outlives the foreground app crashing. Described by its own `sce_sys/param2.sfo`. Attempted as automatic crash recovery and abandoned: the shell resolves it through its installed-titles database, and nothing we control can add a title there. See [ADR-0011](adr/0011-crash-recovery-without-taihen.md). Note VitaSDK's `bgapputil.h` documents the mode argument and the error constant **both off by one**. |
| **Promote** | Registering a directory as an **installed title** in the shell's database — what VitaShell does when it installs a `.vpk`. Copying files into `ux0:app/<TITLEID>` is not enough; an unregistered title cannot be launched and does not appear on the LiveArea. Done through `ScePromoterUtil`, which **refuses to load for us** (`MODULEMGR_NO_LIB`, measured twice, once under a safe self and once unsafe). Consequence: every new title id costs one manual VitaShell install, after which the fast loop owns the slot. **There is a way around it that was measured and not taken**: `ur0:shell/db/app.db` is the shell's installed-titles database, it is ordinary SQLite, and both it and `ux0:app` are writable from an unsafe self — registration is 29 rows in `tbl_appinfo` plus one in `tbl_appinfo_icon`, and that one row *is* the LiveArea bubble. Unexercised because SceShell holds the file open and the corpus needed no new slot. [The recipe](results/title-registration-2026-08-18.md). |
| **VitaShell** | The de facto homebrew file manager. Also hosts the FTP server used for deployment. |
| **VitaDB** | The community homebrew distribution database. Publishing there is the v1 distribution channel. |
| **QEMU** | A CPU emulator: runs armv7 binaries on an x64 or arm64 host. **It cannot run our Vita build** — it emulates the CPU, not the Vita OS, and knows nothing of `sce*` calls. What it can run is a `linux-arm` Dart build, which makes it useful for architecture-level bugs (GC on 32-bit ARM, armv7 codegen) with a real debugger attached and no hardware deploy. Useless for anything touching `sce*`, memory budgets, or timing — and its performance numbers are meaningless, the same trap as Vita3K. Upstream documents the approach in `runtime/docs/qemu.md`. |
| **Vita3K** | Open-source Vita emulator. Fast iteration target, but compatibility is imperfect — **advisory only**, real hardware is ground truth. |
| **PSVshell** | Homebrew overclock/monitoring plugin. Relevant because the 333–500 MHz CPU range is user-controllable, so "the" clock speed is not a single number. |
| **Extended memory mode** | A `param.sfo` flag letting a title claim substantially more than the default user memory budget. The difference between ~200 MB and ~330–400 MB usable. |
| **`sce*` APIs** | Sony's system APIs. The ones we care about: `sceKernel*` (threads, memory, timing), `sceGxm` (GPU), `sceDisplay` (framebuffer/vblank), `sceTouch`, `sceCtrl`, `sceIme` (IME dialog), `sceIo` (file IO), `sceNet` (sockets). |
| **GXM** (`SceGxm`) | The Vita's native low-level graphics API — Sony's Metal or Vulkan, and the only way to talk to the GPU. Proprietary, roughly GLES2-era hardware exposed at a Vulkan-ish level of explicitness. **This project does not render with it** ([ADR-0003](adr/0003-software-rendering-first.md)): Skia draws every pixel on the CPU. It is still required, because a **common dialog** will only composite into a surface GXM manages — which took three pieces of setup and no rendering: `sceGxmMapMemory` on the framebuffer (a pointer valid to the CPU is meaningless to the GPU's MMU), a depth/stencil surface the render-target descriptor demands even though nothing tests depth, and a **sync object**. Leaving the last two null produces a `GPUCRASH` dump **with no faulting thread**: the GPU is asynchronous, so the call returns `0` and validation fails later, when there is no error path left and the driver can only kill the process. |
| **vitaGL** | Community GLES1.1/2.0-ish implementation on top of GXM. The candidate acceleration path in [ADR-0003](adr/0003-software-rendering-first.md), and the best available reference for GXM usage. |
| **VM domain** | A process-wide set of memory blocks allocated by `sceKernelAllocMemBlockForVM` that can be flipped executable (`sceKernelOpenVMDomain`) or non-executable (`sceKernelCloseVMDomain`) **all at once**, with `sceKernelSyncVMDomain` flushing the I-cache. User-mode, no kernel plugin needed. Capped at **16 MiB per block**. The global-toggle granularity is why it suits load-once AOT ([ADR-0005](adr/0005-aot-snapshot-delivery.md)) but not JIT ([ADR-0001](adr/0001-aot-only-no-jit.md)). |
| **Memory budget** | A region reserved at boot by `SceProcessmgr` for a class of process. Varies by firmware and boot flags — so "how much RAM do I get" has no single answer. |
| **Enlarged memory mode** | A title attribute requesting extra user memory, documented in +29 MiB / +77 MiB / +109 MiB variants. Requested via `param.sfo`. Whether homebrew reliably receives it is a Phase 0.5 open item. |
| **LOWPHYMEM** | A reduced-memory launch mode, relevant because plugins like LowMemMode use it to run apps alongside an enlarged-memory title. |
| **emutls** | Emulated thread-local storage. `thread_local` normally compiles to a couple of instructions against a per-thread register, but **VitaSDK has no ELF TLS**, so GCC lowers every access to a call to `__emutls_get_address`. libgcc's implementation is unusable here in two ways — by default `__gthread_active_p()` is a weak reference to `pthread_cancel` that never links, making every `thread_local` **one shared global across all threads**; forcing it in crashes instead, because it guards its table with a statically initialised pthread mutex VitaSDK does not support. So [patch 0009](../patches/dart-sdk/0009-vita-emulated-tls.patch) replaces it. Load-bearing: Dart reads `Thread::Current()` from allocation slow paths, GC and safepoints. Its 32-entry table, never releasing a slot on thread exit, was the [non-deterministic crash](HANDOFF-nondeterministic-crash.md) that cost two sessions. |
| **newlib** | The C library VitaSDK uses. Embedded-oriented: several POSIX facilities the Dart runtime expects are missing, stubbed, or subtly different. The main source of Phase 1 risk. |

## Flutter / Dart

| Term | Meaning |
|---|---|
| **Embedder** | The platform-specific host program that owns the window/surface, drives the event loop, and calls into the engine through `embedder.h`. **This project's core deliverable.** |
| **`embedder.h`** | The stable C API the engine exposes to embedders. Lives at `shell/platform/embedder/embedder.h` in the engine tree. |
| **Engine** | The C++ layer: Skia, libtxt, ICU, the Dart runtime, and the shell. Cross-compiled here with VitaSDK. |
| **Framework** | The Dart-side widget/rendering library. Used unmodified. |
| **First frame** / `runApp` | `runApp()` hands the widget tree to the engine; nothing is on screen before that line executes. It matters here because of a common Flutter shape — `await`-ing setup *before* `runApp` (open a database, read settings, init analytics) — where the awaits go through plugins. On a platform with no implementations, one throws and `main()` dies **before anything asked for a frame**: a black screen with no error to read, which is the least informative failure available. Checked across the five corpus apps and it is the *minority* case: four call `runApp` with nothing awaited. That finding is what made [ADR-0012](adr/0012-app-corpus-as-measurement-instrument.md) choose observation over stubbing. |
| **Skia** | The 2D graphics library Flutter used before Impeller. Has a CPU raster backend, which is what we use first. |
| **Impeller** | Flutter's current renderer. Requires Metal/Vulkan/GLES3. Impossible here ([ADR-0002](adr/0002-skia-not-impeller.md)). |
| **libtxt** | The engine's text layout layer over HarfBuzz and ICU. |
| **ICU / `icudtl.dat`** | Unicode data used for line breaking, collation, and word segmentation. The full data file is tens of megabytes; a slimmed build is required. |
| **`gen_snapshot`** | Host-side tool that turns Dart kernel bytecode into a target-architecture AOT snapshot. |
| **AOT snapshot** | The compiled Dart program plus its heap image. Delivered either as an ELF (`--snapshot-kind=app-aot-elf`) or as assembly to be assembled and linked (`app-aot-assembly`). Which one we use is an open question. |
| **`flutter_assets`** | The bundle directory produced by `flutter build bundle`: fonts, images, `AssetManifest`, kernel/snapshot data. |
| **Codegen** / `build_runner` | Dart's convention for generating source before compilation — `freezed`, `json_serializable`, `drift`, `intl_utils`, `flutter_gen`. The generated files are usually **gitignored**, so a fresh clone of a real app does not compile until `dart run build_runner build` has been run, on the host, with a working Flutter SDK. Purely a host-side step and no concern of the port, but it is a build-blocker that looks like a port bug the first time you meet it. Two of the five corpus apps need it. |
| **Task runner** | An engine abstraction for a serialised task queue, usually backed by one OS thread. The engine expects a platform, UI, raster, and IO runner; embedders may merge them. |
| **Vsync callback** | The engine-driven frame pacing hook. The embedder answers with `FlutterEngineOnVsync`, supplying the frame start and target times. |
| **Platform channel** | Named async message pipe between Dart and the embedder. We implement `flutter/textinput`, `flutter/platform`, `flutter/lifecycle`, `flutter/settings`, and our own gamepad channel. |
| **FFI** (`dart:ffi`) | *Foreign Function Interface* — Dart calling a C function **directly**, in the same process, synchronously, at a real memory address. The other way a package reaches native code, and the one that cannot be rescued here. A **platform channel** sends a named message somebody can answer, so an unanswered call throws `MissingPluginException` and we can supply the answer; FFI sends nothing and wants an address, obtained by asking the **dynamic loader** for a shared library that does not exist. The difference in cost is the whole point: a missing channel implementation is a morning's work, a missing shared library is a cross-compile of somebody else's C. [ADR-0013](adr/0013-ffi-needs-static-linking.md) turns that into an admission test for the app corpus. |
| **Federated plugin** | The standard shape of a Flutter package with native code: a Dart-facing API package, a `platform_interface` package defining the contract, and one implementation package per platform, each declaring itself under `flutter.plugin.platforms` in its `pubspec.yaml`. Platforms the plugin does not declare simply have no implementation — calls throw `MissingPluginException` at runtime. **This is the mechanism by which "run any app from GitHub" is gated on work nobody has done for Vita**, since a platform Google does not ship is a platform no plugin declares. |
| **Registrant** | `GeneratedPluginRegistrant`, the file the Flutter tool generates at build time to wire each resolved plugin's native implementation into the embedder. Every platform has one; Vita has none. [ADR-0004](adr/0004-static-single-binary.md)'s single static ELF means ours would have to register at link time rather than dynamically. |
| **Platform view** | Embedding native UI inside the Flutter scene. Not supported here and not planned. |
| **Blit** | "Block image transfer" — copying a rectangle of pixels between memory regions. Here: copying Skia's CPU-rasterised buffer into the GXM framebuffer the display scans out. Literally a `memcpy` of 960×544×4 = 2.09 MB, measured at **8.06 ms** on hardware. It is the **hard floor** of a software frame because it happens regardless of what changed — `FlutterSoftwareRendererConfig` hands the embedder the whole buffer with no damage information. On a GPU platform this cost does not exist; the renderer draws straight into the scanout buffer. See [ADR-0006](adr/0006-performance-bar-set-from-measurement.md). |

## Project-specific **(ours)**

| Term | Meaning |
|---|---|
| **Supervisor** **(ours)** | `templates/vita-app/supervisor.c`, built as `eboot2.bin`. A tiny **background app** that listens on port 1342 and relaunches the loader, so a crash costs no human. Built and **not reachable** — see the background-app entry. |
| **Bail-out** **(ours)** | `vita_bail_to_loader()` in `templates/vita-app/bailout.c`: record a reason, launch the loader, `sceKernelExitProcess`. Nothing user-mode can catch a data abort here, so instead of catching crashes the port **avoids producing them** — a process that exits cleanly puts up no error dialog, so there is nothing to dismiss and no bubble to find. Hooks in by overriding `abort()` and `__assert_func()`, which needs no engine rebuild because both are *undefined* in the engine archive. [ADR-0011](adr/0011-crash-recovery-without-taihen.md). |
| **Handoff** **(ours)** | The app's dev-server command that launches the loader and exits. An app cannot replace its own `eboot.bin` — its install directory is the read-only `app0:` mount — so it hands control to the loader, which can. This is why a deploy needs no tap while the app is alive. |
| **Runtime port** | The Dart VM's OS abstraction layer implemented for Vita: `os_vita.cc`, `os_thread_vita.cc`, `virtual_memory_vita.cc`, etc. Lives in `runtime-port/` before being applied to the vendored tree as patches. |
| **`flutter-vita`** | Host-side Dart CLI wrapping build → snapshot → link → package → deploy → logs. Lives in `cli/`, launched by `cli/flutter-vita`. Earlier docs call it `flutter_vita_tool`. |
| **`psvita`** | The Dart companion package: raw gamepad and stick state, rear touch, motion, device info, `Vita.isVita`, and runtime configuration of the embedder's input synthesis. **Only what Flutter has no concept of** — D-pad navigation is not in here, because the framework already does it ([ADR-0010](adr/0010-input-layering-and-psvita-api.md)). Earlier docs call it `vita_platform`. |
| **Layer 1 / Layer 2** | The input split from [ADR-0010](adr/0010-input-layering-and-psvita-api.md). Layer 1 is embedder-side synthesis into concepts Flutter already has — D-pad to arrow keys, enter button to `gameButtonA`, left stick to scroll — and needs no package, so unmodified apps get it. Layer 2 is `psvita`, for everything with no Flutter equivalent. The split is also the cost split: layer 1 is plain C structs, layer 2 needs `StandardMethodCodec` hand-encoded in C. |
| **`vita/gamepad` channel** | Our custom platform channel carrying button and analog-stick state. Note the plan text uses both `vita/input` and `vita/gamepad`; **`vita/gamepad` is canonical**, `vita/input` is a doc bug. |
| **M1–M4** | The four milestone gates. M1 = pure-Dart AOT hello world on hardware. M2 = engine links clean. M3 = counter app on hardware. M4 = third party can reproduce the build. |
| **Ground truth** | Real hardware. Any claim about behaviour or performance sourced from Vita3K must say so explicitly. |
| **Vertical slice** | A thin end-to-end path through every layer, built before any layer is complete. M1 is the canonical one. |
| **Spike** | A time-boxed throwaway experiment run to answer one specific technical question. You are buying information, not building product; the code is expected to be discarded. From XP. |
| **Harness** | The scaffolding around an experiment that runs it and reports results, as in "test harness". |
| **Spike harness** | Here specifically: the single C program packaged as a `.vpk` that answers [Track A](phase-0.5-feasibility.md#sequencing) — VM-domain execution, allocation limits, and raster timings — and prints the numbers to a log. Its *code* is disposable, but the build script, packaging, deploy, and logging around it are not: they become the permanent inner loop, which is why it doubles as the Phase 0 hello-world. |
| **Engine artifact** | The redistributable `flutter-engine-vita-<version>.tar.gz` built by `tools/package-engine.sh`: stripped static objects, `embedder.h`, `icudtl.dat`, a font, the dev-server sources, a host `gen_snapshot`, and `MANIFEST.txt`. **63 MB** as of 3.44.8 — the figure was 20 MB when this entry was written. It exists so a developer can build a Vita app **without an engine checkout** — the single largest lever on the toolchain goal, because the alternative is a multi-hour build on their machine. |
| **Conformance app** | The example app that exercises every capability the toolchain claims to expose, used as both an acceptance gate and the benchmark workload that optimization is measured against. Note "capability", not "hardware": it can only reach hardware that layer 1 or `psvita` surfaces to Dart, so **the API precedes the app.** |
| **App corpus** | A set of real third-party Flutter apps used to find bugs the **conformance app** cannot, because that one was written by the people who wrote the engine and cannot probe a capability nobody thought of. Checkouts are gitignored; the **manifest** — repo URL plus commit SHA per app — is committed, or a bug found in an app is a bug that can never be regression-tested. Five apps, one per axis, and one of them is a deliberately plugin-free **control**: without an app that must pass, five failures cannot distinguish a broken port from a broken harness. Its output is a diff, not a verdict — see [ADR-0012](adr/0012-app-corpus-as-measurement-instrument.md). |
| **Toolchain user** | The person the project is for: a Flutter developer with a hacked Vita and no VitaSDK knowledge. Distinct from the **maintainer**, who has the full repo, a vendored engine tree, and hardware on the desk. Every DX claim must name which of the two it is about — several current tools work only for the maintainer, because they read `VERSIONS.md` out of the repo working tree. |
| **Player** | The **toolchain user's** user: the person who installs a finished `.vpk` on their own hacked Vita and plays the app. Not our audience — see [ADR-0015](adr/0015-four-products-one-audience.md). The product boundary ends at the `.vpk`, so a player never installs the **loader**, and player-facing instructions are the developer's to write. Named here because "user" was ambiguous between these two for most of the project's life. |
| **Loader** | The developer-only `.vpk` that receives from the CLI: installs an app into its slot, launches it, streams logs and crash dumps back over TCP, and is where a crashed app returns to. It is what makes the edit-run loop survive a fault without anyone walking to the console, and it is deliberately **not** an FTP server — its `get`/`put` commands exist precisely so BGFTP can stay out of the loop. Since [ADR-0016](adr/0016-the-loader-becomes-a-flutter-app.md) it is itself a Flutter app, on a **pinned engine** and rendering in software, with a C layer holding the port underneath. It **exits when it launches an app**, which is why its on-screen log is always short. See [ADR-0011](adr/0011-crash-recovery-without-taihen.md). |
| **Pinned engine** | The specific, deliberately blessed engine build the **loader** links, as opposed to the one under development. The loader exists to deploy fixes, so it must not share a failure with the thing being fixed: a broken engine can cost you your app and never your ability to replace it. Bumped by an explicit command, never as a side effect of rebuilding. |
| **App slot** | The `ux0:app/<title-id>/` directory an app is installed into, named by its **title id**. `FVTA00002` is the fixed slot the dev loop reuses; a real app derives its own from its package name so that reinstalling replaces rather than accumulates. One app per slot, so two apps sharing a title id overwrite each other. |
| **`gen_snapshot`** | The Dart AOT compiler, which turns Dart source into an ARM snapshot. The one piece of the **engine artifact** that is **host**-specific rather than target-specific: the 63 MB static archive is Vita code and identical everywhere, but `gen_snapshot_armv7` must be built per developer OS. This is why supporting three host platforms is cheap — it costs three small binaries per Flutter revision, not three copies of the archive. |
| **Runtime package** | The pub package giving an app in-process Dart APIs for Vita behaviour — button mapping, suspend/resume, memory pressure. Distinct from the `vita:` block in `pubspec.yaml`, which is **build** configuration read by the build scripts and never present at run time. Keeping the two apart is deliberate: the build block is parsed by both bash and Dart, so it stays flat, while the runtime package has no such constraint. |
| **Scene** | The unit of the gallery's benchmark: one animation, driven by the app itself, run to completion and repeated ([ADR-0017](adr/0017-the-gallery-becomes-the-benchmark.md)). Measurement covers only the animation, never the idle around it — a 300 ms page push sampled over a two-second window is three-quarters idle, and the idle drags every average toward 60 fps. Each scene carries a `stresses` tag naming the renderer primitive it leans on, which is a label rather than a measurement and is marked as such. |
| **Stall** | Two or more consecutive frames at or below 30 fps, i.e. an interruption of 66.7 ms or longer. The benchmark's definition of *problematic*. The "two or more" is load-bearing: at 60 Hz every frame period is a multiple of 16.67 ms, so a frame that misses a single deadline already presents at 33.3 ms and reads as exactly 30 fps — a literal "below 30 fps" rule would therefore fire on every dropped frame on a console where nearly every scene drops one. |
| **Baseline** | The committed results file the benchmark gates against. A scene regressing more than 10% on its **worst-frame** time fails the run — worst-frame rather than mean, because that is the number the stall rule is made of. The file records the conditions it was taken under (clocks, renderer, engine revision, app build), because the 444 MHz change moved every number in the project and nothing caught it. A baseline that does not say what it was measured on becomes a lie without ever being edited. |

**Bad build** — the UI-thread time in a typical *slow* frame of a scene, taken
as the median of the five slowest. Distinct from `build_ms`, which is a median
over every frame: on a route scene most frames are the transition coasting, so
`build_ms` reads 1.2 ms while the frame that builds the incoming page takes 46.
Distinct also from the largest single build, which on every scene is its cold
first frame. See [ADR-0017](adr/0017-the-gallery-becomes-the-benchmark.md).
