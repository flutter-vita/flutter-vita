# Glossary

Shared vocabulary for `flutter-vita`. Two worlds collide in this project — the
Flutter/Dart world and the Vita homebrew world — and most confusion comes from
a term meaning something specific in one of them. Terms marked **(ours)** are
project-invented and should be used consistently in code and PRs.

## Vita platform

| Term | Meaning |
|---|---|
| **VitaSDK** | The community toolchain for PS Vita homebrew. Target triple `arm-vita-eabi`, C library is newlib. Ships headers and stub libraries for Sony's `sce*` APIs. |
| **HENkaku / h-encore** | Homebrew enablers for retail Vita firmware. They are what makes an unsigned title runnable at all. Assumed present on any target device. |
| **taiHEN** | The plugin framework HENkaku installs. Kernel plugins run through it. Explicitly *not* a dependency of this project ([ADR-0001](adr/0001-aot-only-no-jit.md)). |
| **ELF** | Executable and Linkable Format — the standard Unix binary container. Header (`e_machine`, `e_flags` — how the float ABI was verified), sections (`.text`, `.rodata` — the source of every size number here, plus `.ARM.attributes`), and segments (`PT_NOTE`, where `NT_GNU_BUILD_ID` lives). The Vita's SELF is an ELF variant, which is why the whole build pipeline composes: `.elf` → `.velf` → `eboot.bin` → `.vpk` is a chain of transformations on one format, not conversions between formats. |
| **SELF** | Signed ELF. The executable format the Vita loads. Produced from a plain ELF by `vita-make-fself`. Homebrew uses a "fake" self signature. |
| **eboot.bin** | The main SELF of a title, at `app0:/eboot.bin`. Our single statically linked binary ([ADR-0004](adr/0004-static-single-binary.md)). |
| **suprx** | A Vita shared module (dynamic library equivalent). Avoided by ADR-0004. |
| **VPK** | The distribution package: a zip containing `eboot.bin`, `sce_sys/` metadata, LiveArea assets, and the app's data. Built by `vita-pack-vpk`. |
| **SFO** | `param.sfo`, the title metadata blob (title ID, name, category, memory-mode flags). Generated by `vita-mksfoex`. Notably carries the extended-memory request. |
| **Title ID** | Nine characters, e.g. `FLTR00001`. Identifies a title and determines its `ux0:app/<TITLEID>` install path. Must be unique per app. |
| **LiveArea** | The Vita's per-title home screen panel. A VPK needs its background, icon, and startup image or the title looks broken even when it runs. |
| **app0:** | The read-only mount of the running title's own install directory. Where `flutter_assets` and the ICU data will live. |
| **ux0:** | The main writable storage mount (memory card / internal). Per-app writable data goes to `ux0:data/<app>/`. |
| **VitaShell** | The de facto homebrew file manager. Also hosts the FTP server used for deployment. |
| **VitaDB** | The community homebrew distribution database. Publishing there is the v1 distribution channel. |
| **QEMU** | A CPU emulator: runs armv7 binaries on an x64 or arm64 host. **It cannot run our Vita build** — it emulates the CPU, not the Vita OS, and knows nothing of `sce*` calls. What it can run is a `linux-arm` Dart build, which makes it useful for architecture-level bugs (GC on 32-bit ARM, armv7 codegen) with a real debugger attached and no hardware deploy. Useless for anything touching `sce*`, memory budgets, or timing — and its performance numbers are meaningless, the same trap as Vita3K. Upstream documents the approach in `runtime/docs/qemu.md`. |
| **Vita3K** | Open-source Vita emulator. Fast iteration target, but compatibility is imperfect — **advisory only**, real hardware is ground truth. |
| **PSVshell** | Homebrew overclock/monitoring plugin. Relevant because the 333–500 MHz CPU range is user-controllable, so "the" clock speed is not a single number. |
| **Extended memory mode** | A `param.sfo` flag letting a title claim substantially more than the default user memory budget. The difference between ~200 MB and ~330–400 MB usable. |
| **`sce*` APIs** | Sony's system APIs. The ones we care about: `sceKernel*` (threads, memory, timing), `sceGxm` (GPU), `sceDisplay` (framebuffer/vblank), `sceTouch`, `sceCtrl`, `sceIme` (IME dialog), `sceIo` (file IO), `sceNet` (sockets). |
| **GXM** | The Vita's native low-level graphics API. Proprietary, roughly GLES2-era hardware exposed at a Vulkan-ish level of explicitness. |
| **vitaGL** | Community GLES1.1/2.0-ish implementation on top of GXM. The candidate acceleration path in [ADR-0003](adr/0003-software-rendering-first.md), and the best available reference for GXM usage. |
| **VM domain** | A process-wide set of memory blocks allocated by `sceKernelAllocMemBlockForVM` that can be flipped executable (`sceKernelOpenVMDomain`) or non-executable (`sceKernelCloseVMDomain`) **all at once**, with `sceKernelSyncVMDomain` flushing the I-cache. User-mode, no kernel plugin needed. Capped at **16 MiB per block**. The global-toggle granularity is why it suits load-once AOT ([ADR-0005](adr/0005-aot-snapshot-delivery.md)) but not JIT ([ADR-0001](adr/0001-aot-only-no-jit.md)). |
| **Memory budget** | A region reserved at boot by `SceProcessmgr` for a class of process. Varies by firmware and boot flags — so "how much RAM do I get" has no single answer. |
| **Enlarged memory mode** | A title attribute requesting extra user memory, documented in +29 MiB / +77 MiB / +109 MiB variants. Requested via `param.sfo`. Whether homebrew reliably receives it is a Phase 0.5 open item. |
| **LOWPHYMEM** | A reduced-memory launch mode, relevant because plugins like LowMemMode use it to run apps alongside an enlarged-memory title. |
| **newlib** | The C library VitaSDK uses. Embedded-oriented: several POSIX facilities the Dart runtime expects are missing, stubbed, or subtly different. The main source of Phase 1 risk. |

## Flutter / Dart

| Term | Meaning |
|---|---|
| **Embedder** | The platform-specific host program that owns the window/surface, drives the event loop, and calls into the engine through `embedder.h`. **This project's core deliverable.** |
| **`embedder.h`** | The stable C API the engine exposes to embedders. Lives at `shell/platform/embedder/embedder.h` in the engine tree. |
| **Engine** | The C++ layer: Skia, libtxt, ICU, the Dart runtime, and the shell. Cross-compiled here with VitaSDK. |
| **Framework** | The Dart-side widget/rendering library. Used unmodified. |
| **Skia** | The 2D graphics library Flutter used before Impeller. Has a CPU raster backend, which is what we use first. |
| **Impeller** | Flutter's current renderer. Requires Metal/Vulkan/GLES3. Impossible here ([ADR-0002](adr/0002-skia-not-impeller.md)). |
| **libtxt** | The engine's text layout layer over HarfBuzz and ICU. |
| **ICU / `icudtl.dat`** | Unicode data used for line breaking, collation, and word segmentation. The full data file is tens of megabytes; a slimmed build is required. |
| **`gen_snapshot`** | Host-side tool that turns Dart kernel bytecode into a target-architecture AOT snapshot. |
| **AOT snapshot** | The compiled Dart program plus its heap image. Delivered either as an ELF (`--snapshot-kind=app-aot-elf`) or as assembly to be assembled and linked (`app-aot-assembly`). Which one we use is an open question. |
| **`flutter_assets`** | The bundle directory produced by `flutter build bundle`: fonts, images, `AssetManifest`, kernel/snapshot data. |
| **Task runner** | An engine abstraction for a serialised task queue, usually backed by one OS thread. The engine expects a platform, UI, raster, and IO runner; embedders may merge them. |
| **Vsync callback** | The engine-driven frame pacing hook. The embedder answers with `FlutterEngineOnVsync`, supplying the frame start and target times. |
| **Platform channel** | Named async message pipe between Dart and the embedder. We implement `flutter/textinput`, `flutter/platform`, `flutter/lifecycle`, `flutter/settings`, and our own gamepad channel. |
| **Platform view** | Embedding native UI inside the Flutter scene. Not supported here and not planned. |
| **Blit** | "Block image transfer" — copying a rectangle of pixels between memory regions. Here: copying Skia's CPU-rasterised buffer into the GXM framebuffer the display scans out. Literally a `memcpy` of 960×544×4 = 2.09 MB, measured at **8.06 ms** on hardware. It is the **hard floor** of a software frame because it happens regardless of what changed — `FlutterSoftwareRendererConfig` hands the embedder the whole buffer with no damage information. On a GPU platform this cost does not exist; the renderer draws straight into the scanout buffer. See [ADR-0006](adr/0006-performance-bar-set-from-measurement.md). |

## Project-specific **(ours)**

| Term | Meaning |
|---|---|
| **Runtime port** | The Dart VM's OS abstraction layer implemented for Vita: `os_vita.cc`, `os_thread_vita.cc`, `virtual_memory_vita.cc`, etc. Lives in `runtime-port/` before being applied to the vendored tree as patches. |
| **`flutter_vita_tool`** | Host-side Dart CLI wrapping build → snapshot → link → package → deploy → logs. |
| **`vita_platform`** | Dart companion package exposing the gamepad channel, screen metrics, IME helpers, and D-pad focus traversal as a typed API. |
| **`vita/gamepad` channel** | Our custom platform channel carrying button and analog-stick state. Note the plan text uses both `vita/input` and `vita/gamepad`; **`vita/gamepad` is canonical**, `vita/input` is a doc bug. |
| **M1–M4** | The four milestone gates. M1 = pure-Dart AOT hello world on hardware. M2 = engine links clean. M3 = counter app on hardware. M4 = third party can reproduce the build. |
| **Ground truth** | Real hardware. Any claim about behaviour or performance sourced from Vita3K must say so explicitly. |
| **Vertical slice** | A thin end-to-end path through every layer, built before any layer is complete. M1 is the canonical one. |
| **Spike** | A time-boxed throwaway experiment run to answer one specific technical question. You are buying information, not building product; the code is expected to be discarded. From XP. |
| **Harness** | The scaffolding around an experiment that runs it and reports results, as in "test harness". |
| **Spike harness** | Here specifically: the single C program packaged as a `.vpk` that answers [Track A](phase-0.5-feasibility.md#sequencing) — VM-domain execution, allocation limits, and raster timings — and prints the numbers to a log. Its *code* is disposable, but the build script, packaging, deploy, and logging around it are not: they become the permanent inner loop, which is why it doubles as the Phase 0 hello-world. |
